01 / PURPOSE & VISION

Better foundations.
More people to build them.

Our mission is to verify the small set of libraries that most software depends on, in the open, to a standard anyone can re-check.

And to train enough people that this work no longer depends on a small set of experts.

The future we’re working toward

Essential software with public, checkable evidence behind it. A growing community of verifiers. And a commons of reusable proofs that makes each new project easier than the last.

One programme. Two reinforcing parts.

The factory ships real verified modules. The academy turns that work into training. Graduates build the next modules, and reusable lemmas flow back to Mathlib and CSLib.

FIRST PILOT · BUILT, NOT YET VERIFIED · OCTOBER 2026

Keep an archive
inside its boundaries.

The tar pilot's goal is a proved rule for an in-memory ustar extraction model: no accepted path can escape the destination. Its proofs check, but the bar audit of 2026-10-24 found that the main theorem states less than that rule. The audit lists the fixes.

The boundary of the claim: it does not write extracted files to disk. Filesystem integration, races, the parser, checksums, and archive writer are outside the proved guarantee.

03 / OUR PUBLIC STANDARD

“Verified” is a claim
you should be able to check.

A proof establishes that code follows a specification. The specification can still be wrong. Our standard combines independent review, machine checking, adversarial testing, and a clear account of what remains outside the proof.

Read the full verified bar
  1. 01

    A public, independently reviewed specification

    Someone other than the author approves what the code is meant to do.

  2. 02

    No gaps passed off as proofs

    No sorry or admit in the build.

  3. 03

    Visible assumptions

    Main theorems report only standard Lean axioms through #print axioms.

  4. 04

    Recorded differential tests

    Compare against the original implementation. Publish input counts, seeds, and results.

  5. 05

    Explicit trust boundaries

    List what remains unproved, including the runtime, compiler, hardware, and unverified code.

  6. 06

    A reproducible re-check

    A stranger can clone the repository and check the proof with one command.

04 / INSIDE THE FACTORY

From a useful question
to a maintained proof.

Seven steps. A named owner and a check at each one. Shipping is the beginning of a maintenance commitment.

[ ✓ ]

Agents propose.
The kernel checks.
A human owns the specification and the merge.

Read the factory plan
01 Pick the target

Score the candidate, talk to upstream maintainers, and freeze the original tests, public specification, and sample files.

02 Write the specification

State valid inputs, allowed errors, and invariants in Lean. A reviewer who did not write the specification must approve it.

03 Build for proof

Use pure, total functions in Lean. Invalid inputs return an error. Keep the implementation simple enough to reason about.

04 State and prove the theorems

Prove the main claims and supporting lemmas. Treat a failed proof as a bug report against the code, specification, or missing reasoning.

05 Attack the result

Check for proof gaps and unexpected axioms. Run random and mutated inputs against the original implementation. Record what failed.

06 Ship with the evidence

Offer upstream a Lean library, or a Lean model and production implementation kept in step by differential tests. Publish proof limits and benchmarks.

07 Maintain the guarantee

The standard calls for proof checks in CI. A broken proof blocks a release until it is repaired or a specification change is reviewed and recorded.

05 / THE ACADEMY

Learn by shipping.
Leave with proof.

Lectures support the work. They don’t replace it. The academy model moves from a first checked proof to responsibility for a complete module.

  1. LEVEL 0 02 weeks

    Reader

    Learn Lean basics, read proofs, and work through a small codec proof.

    PROOF OF WORKOne small proof, checked by a mentor.
  2. LEVEL 1 08 weeks

    Apprentice

    Own one lemma or parser function and its tests inside a live factory project.

    PROOF OF WORKA contribution merged into a public project.
  3. LEVEL 2 06 months

    Verifier

    Own a module: specification, code, proofs, tests, and its public evidence page.

    PROOF OF WORKA module that passes independent review.
  4. LEVEL 3 Lead & teach

    Spec Lead & Mentor

    Write and review specifications, lead a squad, and train the next apprentices.

07 / HOW WE HOLD THE LINE

A commons, in practice.

Public benefit is the reason for the programme. The way we choose, fund, and review work has to reflect it.

Public work stays public.

Specifications, code, proofs, and test evidence for open libraries remain open. Useful lemmas and fixes go back upstream.

≠

Priority isn’t approval.

Grants and donations support the public factory. Sponsors can move a library up the queue; they cannot buy the verified label.

Keep the scope honest.

Bounded modules, not entire systems at once. Lean 4, Mathlib, and CSLib, rather than a new prover. Clear limits on every claim.

The funding plan keeps paid training and private work a minority of total effort, with the split capped in the annual plan and reported. Read the funding principles
